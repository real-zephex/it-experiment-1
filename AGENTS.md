# AGENTS.md — Agent Guidelines for this Repository

This file instructs automated agents (and human collaborators) how to work in this repository. It focuses on concrete commands, style rules, and safety procedures. Important: every agent must use `bun` as the package manager — do not use `npm` or `yarn`.

Quick facts
- Framework: Next.js 16.1.6 with React 19 and TypeScript 5
- Package manager: `bun` (required)
- TypeScript target: ES2017+ (see `tsconfig.json`)

Development, build, lint & test commands (use bun)

Installation

```bash
# Install dependencies
bun install
```

Run / build / start

```bash
# Start dev server (local)
bun run dev

# Build production bundle
bun run build

# Start production server
bun start
```

Linting & type checks

```bash
# Run ESLint across repo
bun run lint

# Lint a single file
bun run lint -- path/to/file.ts

# Type check everything with TypeScript (no emit)
bun tsc --noEmit

# Type check a single file
bun tsc --noEmit path/to/file.ts
```

Tests
- This repo currently has no dedicated test framework configured. Agents should prefer lightweight checks, but when adding tests use Bun's built-in test runner or Vitest.

Examples:

1) Bun test runner (recommended if tests added):

```bash
# Run all tests
bun test

# Run a single test file
bun test path/to/testfile.test.ts
```

2) Vitest / Jest (only if added by a human):

```bash
# After adding test script (e.g. "test": "vitest")
bun run test -- path/to/testfile.test.ts
```

If you only need a quick static verification, prefer `bun tsc --noEmit path/to/file.ts`.

Code style & conventions

TypeScript and naming
- Use PascalCase for component names, types and interfaces: `UserProfile`, `CreatePostDto`.
- Use camelCase for functions and variables: `getUserData`, `handleSubmit`.
- Use CONSTANT_CASE for global constants: `MAX_POST_LENGTH`.
- Avoid implicit `any`. Prefer concrete types; use `unknown` and narrow when necessary.
- Prefer named exports. Use default exports only for legacy reasons.

Imports ordering
- 1) React / Next imports
- 2) Third-party packages
- 3) Absolute imports (alias `@/` configured in tsconfig)
- 4) Relative imports

Formatting rules
- Line length: keep under 120 characters
- Indentation: 2 spaces
- Semicolons: always present
- Trailing commas: use in multi-line arrays/objects
- Strings: use double quotes

React & Next.js patterns
- Prefer Server Components (default) for pages/layouts. Add `"use client";` only to components that need client-side behavior.
- Export components with explicit return types: `export default function Home(): React.ReactNode { ... }`.
- Put props interfaces at top of the file.

Styling
- Use Tailwind CSS utility classes. Compose classes with `cn()` helper (`lib/utils.ts`) + `clsx`/`tailwind-merge` where needed.
- Prefer class composition over inline styles. Only use inline style objects for dynamic runtime-only values.

Error handling & validation
- Use Zod for runtime validation at API boundaries and Convex functions.
- For async operations use try/catch and return clear user-facing errors while logging full details in development only.
- Never return stack traces or secrets to clients.

Type safety & discipline
- `tsconfig.json` uses `strict: true`. Do not relax this.
- Always annotate exported function return types.
- Use discriminated unions for complex state shapes.

Backend and Convex patterns
- Convex server and client code live in `convex/`.
- Put data access logic in Convex functions and enforce authorization there (server-side RBAC).
- Use validators and types generated by Convex (`convex/_generated`) when available.

Auth & environment
- Authentication uses Clerk; tokens and keys live in `.env.local` (do not commit this file).
- Required env vars (examples) — place these in `.env.local`:

```
NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY=...
CLERK_SECRET_KEY=...
NEXT_PUBLIC_CONVEX_URL=...
```

Pre-submit checklist (what agents should run before creating changes)

1) Type check: `bun tsc --noEmit`
2) Lint changed files: `bun run lint -- path/to/file` and/or `bun run lint`
3) Build: `bun run build` (catch build-time errors)
4) Smoke test: run dev server `bun run dev` and manually verify main flows
5) Secrets check: ensure `.env.local` and any secrets are not committed

Git & commit guidance for agents
- Do NOT push changes to remote without explicit human instruction.
- Do not use destructive git commands (`git reset --hard`, `git checkout --`, force push) unless explicitly approved by a human.
- If asked to create commits, stage only intended files and provide a concise commit message describing the why.

Security considerations
- Never commit `.env.local` or other secret files.
- Validate all inputs at the server boundary (use Zod/Convex validators).
- Enforce RBAC in server functions, not only in client UI.

Troubleshooting & tips
- `bun: command not found` — install Bun: `curl -fsSL https://bun.sh/install | bash`
- Lint autofix: `bun run lint -- --fix`
- If Next serves stale content: `rm -rf .next/` and rebuild

Zod usage example

```ts
import { z } from "zod";

const PostSchema = z.object({
  title: z.string().min(5).max(200),
  content: z.string().min(10),
});

try {
  const data = PostSchema.parse(input);
} catch (err) {
  if (err instanceof z.ZodError) {
    console.error("Validation failed:", err.errors);
    throw new Error("Invalid input");
  }
  throw err;
}
```
